# Подключение Java backend

## Текущее состояние

«Играть» вызывает гостевой доступ, затем `POST /api/v1/sessions/generated`
с телом `{}` и UUID команды. После успешной генерации открывается анкета
по данным character, а ID сохраняется как активный. «Начать жизнь»
открывает это же сохранение, без ещё одного POST создания.
Кнопка «Продолжить жизнь» получает последнее обновлённое сохранение через список
и загружает его. Если сохранений нет или API недоступен, отображается сообщение.
При F5 восстанавливается активный ID, со списком как запасным вариантом.

Оба источника используют `GamePage`. При ошибке генерации показаны сообщение,
повтор и явный выбор «Играть с моковыми данными». Если ответ на действие потерялся, доступен
повтор той же команды. Активный ID хранится в localStorage. F5 по адресу
с `#server-life` загружает игру. Адрес с `#server-birth` восстанавливает анкету
той же жизни. Доступ проверяется по cookie.

Готовы:

- `src/api/client.ts`: HTTP-клиент с таймаутом, отменой через AbortSignal,
  проверкой ответа и различимыми ошибками.
- `src/api/index.ts`: клиент с настройками Vite. Сам запросы не отправляет.
- `src/types/character.ts`: модели UI, независимые от моковых значений.
  Это не утверждённые DTO сервера.
- Прокси `/api` в Vite для локального Java backend.

## Согласованный первый контракт

Изучены backend-файлы `docs/openapi.yaml` (версия 0.4.0) и
`docs/integration.md` из соседнего проекта `life-backend`.
Источник контракта остаётся в backend; копия YAML во frontend не создаётся.

Добавлены `sessionTypes.ts`, `sessionDecoders.ts`, `sessions.ts` и
`characterMapper.ts` в `src/api`. Экспорт `sessionsApi` доступен из
`src/api/index.ts`. Состояние и действия серверного экрана управляются через
`src/game/useServerLife.ts`.

| Операция | Метод API |
| --- | --- |
| Проверка приложения | `GET /api/v1/health` |
| Гостевой доступ | `POST /api/v1/guest`, тело `{}`, ответ 204 |
| Список сохранений | `GET /api/v1/sessions` |
| Создание | `POST /api/v1/sessions` |
| Генерация | `POST /api/v1/sessions/generated` |
| Загрузка | `GET /api/v1/sessions/{id}` |
| Переход года | `POST /api/v1/sessions/{id}/advance` |
| Ответ | `POST /api/v1/sessions/{id}/decisions/{decisionId}/answers` |

Базовый URL клиента остаётся `/api`, методы добавляют `/v1/...`.
Не менять базу на `/api/v1`: иначе получится повторение `/v1`.
Перед операциями сохранений клиент дожидается гостевого доступа. Параллельные
чтения используют один текущий запрос гостя. Cookie хранит браузер;
`credentials: same-origin` подходит для прокси Vite.

Создание команды и её отправка разделены:

```ts
const action = sessionsApi.prepareAdvance(session.id, session.version);
const updatedSession = await action.execute(abortController.signal);
```

При потере ответа повторно вызвать `action.execute()` на ТОМ ЖЕ объекте:
ключ UUID и исходное тело остаются прежними. Создание нового объекта командой
`prepareAdvance` означает НОВОЕ действие. Компонент должен хранить команду
до однозначного результата, блокировать параллельные мутации и сохранять её
на время неопределённого исхода. Сам слой API не является очередью команд
и не восстанавливает незавершённые команды после перезагрузки страницы.

При `error.code === 'VERSION_CONFLICT'` загрузить состояние через `getSession`,
не повторять действие с автоматически подменённой версией. Остальные коды
включают `DECISION_REQUIRED`, `DECISION_CHANGED`, `SESSION_COMPLETE`,
`IDEMPOTENCY_CONFLICT`, `INVALID_REQUEST`, `INVALID_OPTION`,
`SESSION_NOT_FOUND`, `ENGINE_TOKEN_EXPIRED`. Не смешивать 404 с созданием
новой жизни и не переключать её на моки.

`toCreateSessionRequest` сохраняет выбранные настройки и начальные показатели.
Код страны ISO2 и год рождения передаются явно: неизвестную страну нельзя
молча подменять Японией. DTO backend выделены отдельно от модели UI.
При получении проверяются вложенные данные, шкалы, целые числа и статусы.
Версии int64 выше Number.MAX_SAFE_INTEGER отклоняются; для таких значений
backend должен передавать версию строкой с обновлением OpenAPI.

### Ограничения текущего сценария

- `character.birthDetails` — необязательный nullable-снимок рождения из OpenAPI
  0.4.0. Декодер проверяет вложенные родителей, профессии, братьев/сестёр,
  домохозяйство и категории. Один DTO используется для POST generated и GET.
  Полный снимок сохраняется в Session. `toGeneratedBirthCard` отбирает только
  поля Frame 8891:104789: профиль, три характеристики, членов семьи с возрастом
  и профессией, пять строк условий семьи и предусмотренные макетом поля страны.
  Местность показана в строке региона независимо от города. Аура, счастье,
  отношения как отдельная шкала, текущий возраст, коды и технические сведения
  о домохозяйстве на этой странице не выводятся.
  Значения 0, false и пустые списки не считаются отсутствующими. Отсутствие
  собственного жилья не означает аренду. Данные рождения доступны только для чтения.
  «Начать жизнь» по-прежнему открывает полученный ID без повторной генерации.
- В DTO обязателен provider со значением local или 1in8b. Числовые аура
  и внешность могут быть null. Отсутствующие значения скрываются.
- Город рождения может отсутствовать. Анкета использует страну и сведения
  из character. На странице персонажа только параметры макета;
  в отдельном редакторе остаётся полный список настроек:
  неизвестные поля помечаются «Нет данных», без подстановки моковых родственников.
  Кнопка «Поменять параметры» открывает общий редактор. Для `1in8b` доступны
  имя и внешность (включая исходное null), для `local` — также здоровье и интеллект.
  Остальные поля доступны только для просмотра. Токены из моков не списываются.
  `prepareEditCharacter` отправляет только изменённые поддерживаемые поля через
  `PATCH /api/v1/sessions/{id}/character`, с последней версией и UUID команды.
  Успешный ответ заменяет снимок той же жизни; при ошибке редактор остаётся открыт.
  Повтор сохраняет исходные тело и ключ. При конфликте версии загружается свежая
  сессия, черновик сбрасывается и отображается сообщение об обновлении.
- Моковая и серверная анкеты используют общую вёрстку `BirthCharacterPage`.
  Серверные шансы рождения и статистика страны пока не предусмотрены API:
  в соответствующих ячейках показано «Нет данных», значения из моков не подставляются.
- `BirthplaceMap` ставит маркер по countryCode и city из той же анкеты.
  Координаты берутся из локального географического справочника: сначала город,
  затем приблизительная точка страны. Неизвестный ISO2 не подменяется Японией.
  После F5 положение вычисляется из восстановленного места рождения.
  Подробности точности и источники: [map-data-sources.md](map-data-sources.md).
- Для жизни 1in8b в анкете и игре показаны ссылка на движок и отметка о моделировании.
- Первое состояние может иметь возраст больше нуля, ответ на решение тоже
  может изменить возраст. После каждого принятого состояния прогресс нового
  шага отсчитывается заново по версии, даже если целый возраст не изменился.

- Backend хранит целый возраст. `useServerClock` анимирует прогресс локально и
  отправляет одну команду advance на границе года. Возраст берётся из ответа.
  Пауза, ожидающее решение, запрос, ошибка и COMPLETE останавливают таймер.
  После F5 дробный прогресс начинается с сохранённой границы года.
- История приходит от старых событий к новым, сохраняет серверные ID.
- Новые записи очередного ответа показываются постепенно в течение игрового
  года через historyPlayback. API передаёт целый возраст без времени внутри года,
  поэтому интервалы показа равномерные. Исходные возраст, текст и ID сохраняются.
  Пауза и ожидание ответа останавливают показ, скорости меняют его темп.
  При открытии сохранения уже прожитая история доступна целиком. Перед решением
  и при завершении показывается весь полученный контекст.
- Переход года сохраняется в фоне без отдельной карточки загрузки. До ответа
  сервера следующий год не начинается. Ошибки и повтор команды видимы.
- Нет команд покупок, фокуса, переноса решения, финансов, индивидуальной
  близости и избранного. Не отображать моковые значения как серверные.
- Сохранения local используют прежний серверный движок. Сохранения 1in8b
  продолжаются через поставщика. Статус COMPLETE определяет завершение независимо
  от возраста. Локальные моки содержат историю до 22 лет.

Клиент не повторяет запросы автоматически. Это важно для решений и покупок.
HTTP-статус и JSON ошибки доступны в `ApiError.status` и `ApiError.details`.
Сообщения пользователю не содержат сырой HTML или внутренних ошибок сервера.
Отмена пользователем/размонтированием остаётся `AbortError`; таймаут имеет
`ApiError.kind === 'timeout'`.

## Локальный запуск

1. При необходимости скопировать `.env.example` в `.env.local`.
2. Запустить backend отдельно, из VS Code или Docker Compose.
3. Запустить frontend командой `npm run dev`.

Браузер обращается к `/api/...` на адресе frontend. Vite передаёт запрос
на `http://127.0.0.1:8081/api/...`, сохраняя префикс `/api`.
Если сервер использует другой префикс, согласовать конфигурацию.

`DEV_API_TARGET` — адрес, доступный процессу Vite. Когда Vite работает в Windows,
а backend в Docker, нужен опубликованный порт хоста, а не имя сервиса Compose.
При изменении `.env.local` перезапустить Vite.

Проверка Docker backend через frontend — `GET /api/v1/health`.
Напрямую тот же запрос доступен по `http://127.0.0.1:8081/api/v1/health`.
ожидаются HTTP 200 и `{"status":"UP"}`. Ответ 404 не означает проблему CORS
или отсутствие PostgreSQL. Сверить порт, приложение и актуальность сборки;
в текущих исходниках backend HealthController использует именно этот путь.
Перезапуском backend управляет его чат; frontend не должен обходить 404
выбором другого, не описанного в контракте URL.

Vite-прокси работает только при разработке. Для размещения нужен reverse proxy
`/api` на backend либо абсолютный `VITE_API_BASE_URL` и CORS для конкретного
origin frontend. Значения `VITE_*` встраиваются при сборке и публичны.
Секреты в них хранить нельзя.

## Что согласовать с backend-чатом

Первый контракт согласован выше. Следующие пункты относятся к расширению
контракта и подключению оставшихся разделов интерфейса.

Нужны:

1. Методы создания, чтения и восстановления сессии; её идентификатор.
2. DTO персонажа: условия рождения отдельно от текущего местоположения.
   Сейчас пол и страны представлены русскими подписями; серверные коды нужно
   преобразовывать адаптером, а не передавать подписи как ISO-коды.
3. Характеристики, аура, отношения, покупки и история со стабильными ID.
4. Валюта, единицы сумм, период доходов/расходов и журнал операций.
5. Команды ответа, фокуса, покупки, паузы, скорости, автовыбора и отложения.
   Зафиксировать неподдерживаемые внешним движком механики.
6. Гостевой доступ/авторизация и восстановление после перезагрузки.
7. Ошибки, конфликты состояния и ограничения квоты.
8. ID команды для защиты от дублей и версия состояния для одновременных
   действий. Повтор после таймаута использует тот же ID и выясняет результат;
   нельзя просто создавать новую покупку.
9. Поведение закрытой/скрытой вкладки и сохранение дробного прогресса,
   если потребуется расширение текущей схемы целого возраста.

При cookie-авторизации отдельно согласовать CSRF-защиту. Сейчас клиент
использует `credentials: 'same-origin'`; cross-origin cookies требуют
дополнительной настройки клиента, CORS и cookie на backend.

## Расширение серверного режима

1. Согласовать в OpenAPI новые поля и команды для фокуса, покупок, финансов
   и близких. Добавить DTO, проверку JSON и методы в `src/api`.
2. Подключить эти действия к серверному экрану через `useServerLife`.
   Применять возвращённое состояние и отображать ошибки запроса.

Токен 1in8b и API-ключ остаются на backend, не в localStorage.
Разрешение на движок, квоты, совместимость механик и срок токена проверяются
отдельно. Этот этап их готовность не подтверждает.

## Проверки

При `npm run dev` ответы API выводятся в консоль браузера (F12 → Console).
Группы с префиксом `[API]` содержат метод, URL, HTTP-статус, время ожидания
и тело ответа до проверки декодером. Пустые ответы, некорректный JSON,
ошибки HTTP, отсутствие соединения и таймауты также видны в логах.
Cookie и заголовки запросов не выводятся. В production-сборке логирование отключено.

```text
npm test
npm run typecheck
npm run lint
npm run build
```

HTTP-тесты используют подменённый fetch: не требуют backend и не расходуют
квоту. Существующие тесты моковой симуляции продолжают выполняться.

Для проверки включите Preserve log в Network и нажмите «Играть».
Ожидаются POST guest и один POST generated. Повторное нажатие блокируется.
Обновите анкету через F5, проверьте GET той же сессии. Нажмите «Начать жизнь»,
убедитесь в отсутствии нового POST generated. Ответьте на решение,
обновите игру и сравните имя, ID, возраст и историю. Генерация и действия
расходуют квоту внешнего движка.

Для проверки моков используйте кнопку явного выбора после ошибки генерации.
